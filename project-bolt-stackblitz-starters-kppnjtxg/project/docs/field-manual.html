You built an arcade.
Here's what's inside it.

Your game sends players down through a buried complex, one floor at a time. This manual does the same with your code. Each floor is one part of the project: what it does, where it lives, and what you could change next.

Three ideas before you go down

Code is a list of instructions

The computer does exactly what the file says, top to bottom, very fast. A function is a named recipe it can run again and again, like rollRarity for loot.

Files are rooms, folders are floors

Everything that runs in the game is in the src/ folder. The other folders are tools, old copies, and a server that isn't plugged in yet.

A game is a loop

Read the buttons, update the world a tiny bit, draw it, repeat about 60 times a second. Once you see that loop, the rest of the code makes sense.

000 MLiveMM3-0007

The front door

Where the arcade starts, and how it picks which screen you see.

When someone opens the arcade, the browser runs src/main.tsx first. It wraps the whole app in a safety net called an error boundary. If one screen crashes, players get a "Something went wrong" box with a Try again button instead of a blank white page.

Then src/App.tsx takes over. It's the map of the arcade. A small package called wouter reads the web address, like /friends, and shows the matching page. Every page sits inside AppShell, which draws the top bar and footer so they stay put while the middle changes. All the addresses are listed in one place, the Router function at src/App.tsx:357. When you wonder where a page comes from, look there first.

That list holds a surprise. It has only four addresses: the lobby, friends, profile, and /play/deep-signal. Snake, Memory, Tic-Tac-Toe, 2048 and Zombie Sniper are all still in the code, but no address leads to them. Your design notes say to focus on one flagship game first, so this may be on purpose. Either way, they're one route away from coming back.

One visit, step by step
  1. The browser loads index.html, which loads src/main.tsx.
  2. main.tsx starts React inside the error boundary.
  3. The router compares the address with its list of four.
  4. AppShell draws the header, then the page, then the footer.
  5. The page reads your saved name and scores from the browser (floor 048).

012 MLiveMM3-0003

The screen

Draws The Signal Below about 60 times a second and listens to your keyboard and mouse.

BuriedComplexGame.tsx has three jobs. It draws: every frame it paints the floor, walls, enemies, loot and you onto a canvas. It listens: WASD, J, K, Space, E and the mouse are all caught here. And it shows the words: health and stamina bars, floor messages, and the Begin, Continue and Extract panels.

It never decides what happens. Each frame it hands your buttons to the engine on the next floor down and gets the new world back. The screen is the eyes and hands. The engine is the brain.

There's a smart trick in here that real game developers use. React redraws part of the page whenever its state changes, and doing that 60 times a second would be slow. So this file keeps the live game in a ref, a sticky note that doesn't trigger a redraw, and copies it into React state only every 40 milliseconds (line 317). The canvas still moves every frame. Only the bars and text catch up 25 times a second.

One frame, step by step
  1. You press a key. A listener writes it onto a sticky note (lines 262–285).
  2. The browser calls the loop just before it shows the next picture (lines 297–330).
  3. The loop sends your buttons and the time that passed to the engine.
  4. render3DComplex paints the backdrop, sorts everything by depth, and draws it back to front so near things cover far things (lines 79–238).
  5. When a run ends, your score goes up to the front door to be saved.
Where it lives
  • src/components/BuriedComplexGame.tsxThe drawing, the input, the loop, and the panels. 508 lines.
  • src/components/BuriedComplexGame.cssHow the HUD, panels and buttons look, including phone layouts.
canvas
A blank rectangle on the page that code paints pixels onto, like a digital whiteboard.
requestAnimationFrame
A browser helper that runs your function right before each new picture.

A sticky note that holds a value without making React redraw.
024 MLiveMM3-0002

The heartbeat

The rules for one tiny slice of time: moving, swinging, guarding, dodging, getting hit, levelling up, and picking up loot.

Every frame, the screen calls one function: stepDeepSignalRun in src/lib/deep-signal-engine.ts (line 363). It gets three things. The state is everything the game remembers right now: your health, every enemy's position, what's in your bag. The input is which buttons are held. And deltaMs is how many milliseconds passed since the last frame. It returns a brand-new state, one slice of time later.

Delta time is the clever bit. Computers don't run at a perfectly steady speed, so every movement is multiplied by the time that actually passed. A fast laptop and a slow one move you the same distance per second. Line 365 also caps a frame at 50 milliseconds, so if you switch tabs and come back, enemies don't teleport ten seconds forward.

The function never changes the old state. It copies what it needs, changes the copies, and hands back a fresh one at the end. That makes bugs much easier to track down. The downside is size: it's one 320-line function, so you can't test the guard rule on its own without running a whole frame.

Inside one heartbeat
  1. Cap the time and tick down cooldowns: attack, dodge, and the short moment you can't be hurt.
  2. Move you. If you're swinging, hit enemies in reach and knock them back. Your weapon's bonus is added here (line 428).
  3. Enemies chase you, wind up, and strike. Your guard blocks if you have stamina and you're facing them.
  4. Defeated enemies give XP and score and may drop loot. Walk over loot to pick it up.
  5. Room empty? Walk to the relay door. Every 5th floor is a safe room, where you bank your loot or risk it deeper. Floor 100 holds the final boss.
game loop
Read buttons, update the world a little, draw it, repeat.
delta time
How long the last frame took. Multiplying speeds by it keeps movement fair on any computer.
state
The game's memory at one moment: every number it needs to draw the next picture.
036 MLiveMM3-0008

The world builder

Builds every run: the random rooms, the enemies inside them, your starting stats, and how lucky your loot is.

Every run gets a new dungeon built from dice rolls instead of by hand. That's called procedural generation. Each floor drops 3 to 5 blockers (pillars, crates, consoles) in random spots. Every 10th floor is a boss floor with just 2. Rooms start with about 3 enemies and climb to 8, and every third one is a tougher Warden. Enemy health grows 14% per floor, so a floor-50 monster has about 7.9 times the health of a floor-1 one.

Loot luck lives in rollRarity (line 326). It rolls a number from 0 to 100, adds a depth bonus of 0.45 per floor (never more than 35), and checks the total against fixed lines. The deeper you go, the more often you cross the high ones. Legendary can't drop at all before floor 41.

Gear power is the rarity rank times 3, plus 1 for every 3 floors, so a floor-1 Legendary has power 15 and a floor-100 one has 48. You start each run with 110 health and 100 stamina, plus the best shell and module you've banked. Notice the middle three columns never change. Only Common and the top two trade places as you go deeper.

procedural generation
Letting code build levels with random rolls instead of drawing each one by hand.
rarity roll
A random number, plus a bonus, compared against fixed lines to pick how rare a drop is.
seed
A starting number for the dice. The same seed always gives the same rolls, so everyone can play the same dungeon.
048 MLiveMM3-0004

The memory

Remembers your name, friends, best scores and banked gear between visits.

When you finish a game or add a friend, the code packs everything into text and puts it in localStorage, a small notebook the browser keeps for each website. There are two notebooks. src/lib/arcade-store.ts holds your profile, friends and scores. src/lib/deep-signal-store.ts holds your banked gear.

That notebook lives in one browser on one computer. A friend's computer starts blank. Clearing browser data wipes it. And anyone can open the browser's developer tools and change what's written, so these are honest-player scores. A leaderboard nobody can fake needs the kitchen at the bottom of this manual.

This floor is careful work. Before trusting the notebook, isArcadeState (lines 31–46) checks that everything has the right shape. If the save is broken, the game quietly starts fresh instead of crashing. It also only writes when something changes, never every frame.

One save, step by step
  1. A game ends and calls recordGameResult.
  2. The code reads the notebook and turns the text back into data with JSON.parse.
  3. It keeps the higher of your old and new score.
  4. JSON.stringify turns it back into text, and it's written to the notebook.
  5. Next visit: read, check, and use it, or reset if it's damaged.
localStorage
A small per-website notebook the browser keeps on this computer.
JSON
A text format for writing data down, like {"score": 10}.
validation
Checking data before you trust it, like a bouncer checking an ID.
060 MLiveMM3-0011

The paint closet

Colours, fonts and spacing for the whole arcade, plus a box of ready-made parts nobody has opened.

Almost everything you see is styled by one file, src/index.css, written in CSS. The best idea in it is the theme variables: named paint tubes like --primary, mixed once at the top and used everywhere else. Change one tube and every button that uses it changes too.

/* src/index.css:98, the gold paint tube, mixed once */ --primary: 42 91% 60%; /* src/index.css:22, handed to Tailwind so any button can use it */ --color-primary: hsl(var(--primary));

Tailwind adds tiny one-job class names like flex or mt-4. The last 300 or so lines are hand-written rules that give the arcade its look and style each game's pieces.

Then there's src/components/ui/: 55 ready-made parts (buttons, dialogs, menus) from a kit called shadcn/ui. The live arcade uses none of them. The build leaves unused code out of the download, so players don't pay for it. You do, though: 27 extra packages to install and 55 files to wade past.

CSS
The rules for how things look: colour, size, spacing, position.
theme variable
A named colour or size. Change it in one place and it changes everywhere.
Tailwind class
A tiny class name that does one styling job, like flex.

084 MHiddenMM3-0005

The night range

Zombie Sniper, a 3D shooting gallery. Its rules and its picture live in two separate files.

The rulebook

src/lib/zombie-sniper-engine.ts

5-round magazine, 0.95 second reload, 3 lives. 100 points for a body shot, 250 for a headshot. A zombie that reaches the far edge costs a life. Plain functions, no drawing at all.

The picture

src/components/ZombieSniperGame.tsx

A 3D scene built with three.js. Each zombie is about eleven simple shapes (meshes) stuck together. The camera sits just behind the rifle, looking down the field.

That split is the best habit in the whole project. MM3 confirmed that the rulebook never touches drawing code and runs without any screen. You could test every score and reload with no graphics at all, and you could redraw the whole game without breaking the rules.

The weak spot is timing. The rules update 60 times a second, but the picture only refreshes every 90 milliseconds, so zombies hop about 11 times a second instead of gliding.

The viewpoint that decides which part of the 3D space you see.
096 MToolsMM3-0010

The workshop

The tools that turn your code into a website.

npm downloads packages, which are ready-made code other people wrote. package.json is your shopping list. package-lock.json is the exact receipt, so every install gets identical versions. Vite is the kitchen. It serves the game on your computer while you work, and it packs everything into a few small files when you're ready to put it online.

# once, to download the packages npm install # play it on your computer; it reloads when you save a file npm run dev # build the final website into the dist/ folder npm run build

Here's what a real build of your arcade produced: one JavaScript file of 276 kB (87 kB once compressed for download) and one stylesheet of 129 kB (25 kB compressed). That's small for a game with this much in it.

A few things to tidy. react and react-dom aren't on the shopping list even though everything needs them; they only arrive because other packages pull them in. lucide-react is set to "latest", so a reinstall can quietly change your icons. The project mixes two package managers: npm at the top, pnpm settings in .replit, scripts/, artifacts/ and lib/. And artifacts/global-arcade/ is an older copy of the arcade that has drifted away from src/. Only src/ is the real one.

The earlier problem file is already handled. Someone had pasted instructions aimed at AI tools into .npmrc, a settings file. It's now .npmrc.txt, which npm ignores.

Pro tip: keep your version number in one place. Right now "v3.0" is typed by hand in five spots, in App.tsx and BuriedComplexGame.tsx. Bump four and forget one, and the game shows two versions at once. Instead, write it once, like export const VERSION = "3.0", and show it everywhere with v{VERSION}. Next release is a one-line edit. It also gives anything that tracks your releases, like a "What's new" list, one number to read.

package
Ready-made code someone else wrote, downloaded by npm.
lockfile
The receipt of exact versions, so every install matches.
bundle
Your many files squeezed into a few, so the browser downloads less.
184 MSealedMM3-0006

The kitchen

A server, a database and an API. Built, but not plugged into the games.

Everything above this line is the front end, the part you see and touch. The back end runs somewhere else. Think of a restaurant:

dining room
The arcade in your browser.
kitchen
The server, artifacts/api-server/. It waits for orders and sends back answers.
menu
The API, lib/api-spec/openapi.yaml: the exact list of things you can order.
pantry
The database, lib/db/. It keeps data after everything shuts down.
printer
Code generation prints matching code for the kitchen and the dining room from one menu, so they always agree.

Right now the kitchen serves one dish. /api/healthz answers "ok", like a chef calling out "we're open". The database has no tables yet, and nothing in src/ talks to any of it.

This is where your biggest ideas would live: a leaderboard friends can see from any computer, cloud saves, real friend lists. It comes with real responsibility, because other people's data would be in your hands. MM3 was asked "is this ready for real player data?" and the answer was no. Before inviting friends, you'd need:

  • Routes that check who is asking before they answer.
  • Calls allowed only from your arcade. Right now any website could call it (app.ts:53).
  • An encrypted connection to the database.
  • An owner column on each table, so the server knows whose row is whose.
  • Score checks on the server, because anyone can send any number to an API.
API
A fixed list of requests a server accepts, and the answers it promises.
endpoint
One address on the server that does one job, like /api/healthz.
schema
The plan for a database table: which columns it has.

Fix these first

Bugs a player could actually notice, most noticeable first. Each one comes with a message you can paste straight into Claude Code.

  1. Keys get stuck after switching windows

    Hold W, alt-tab away, come back: your explorer keeps walking. The game never hears the key come back up.

    BuriedComplexGame.tsx:262–285 · MM3-0003, 84% sure

    In src/components/BuriedComplexGame.tsx, add a window blur listener in the keyboard useEffect that clears keysRef and resets the attack, guard, dodge and interact flags, so a held key can't get stuck when I switch windows. Show me the change before you apply it.

  2. Enemies can spawn inside crates

    Enemy spawn spots are rolled without checking where the blockers went, so a monster can start stuck in a wall.

    deep-signal-engine.ts:209–210 · MM3-0008, about 96% sure

    In src/lib/deep-signal-engine.ts, createEnemiesForRoom picks random spawn spots that can land inside a blocker. Can you re-roll a spawn spot if it overlaps any blocker in the room, and explain how the check works?

  3. A held dodge can fire twice after a floor change

    When the floor advances, the game forgets that dodge was already held down, so it can dodge again on its own.

    deep-signal-engine.ts:585–597 · found by reading the code

    In src/lib/deep-signal-engine.ts, the early return near line 585 that advances the floor doesn't update dodgeWasDown. Can you fix it so a held dodge button can't trigger a second dodge right after a floor change?

  4. Gear can get duplicate IDs after a reload

    The counter that names new gear starts again at 1 every time the page loads, but your banked gear already uses those names. The gear list can then mix items up.

    deep-signal-engine.ts:126, used as a list key at BuriedComplexGame.tsx:492 · checked by hand

    In src/lib/deep-signal-engine.ts, nextGearId starts at 1 on every page load, so new gear can reuse ids that banked gear already has. Can you make gear ids unique across reloads, for example with crypto.randomUUID(), and check nothing else depends on the old format?

  5. Saves can fail without telling you

    If the browser's notebook is full, an arcade save just doesn't happen and nobody is told. Deep Signal already shows a message for this. The rest of the arcade doesn't.

    arcade-store.ts:60–69 · MM3-0004, 92% sure

    In src/lib/arcade-store.ts, saveArcadeState silently ignores errors. Can you make it return whether the save worked, and show a short message in src/App.tsx when it fails, like the Deep Signal save note does?

  6. Snake can turn into its own neck

    Hidden game

    Press two directions fast enough inside one 145 ms tick and the snake can reverse into itself.

    App.tsx:172 and :184 · found by reading the code; MM3 was unsure (41%)

    In src/App.tsx, SnakeGame checks a new turn against dir.current instead of the pending nextDir, so two quick key presses can reverse the snake into its own neck. Can you fix the turn check?

  7. Memory's shuffle isn't fair

    Hidden game

    Shuffling with sort and a random comparison makes some layouts more likely than others.

    App.tsx:220 · MM3-0009, 91% sure

    In src/App.tsx, the Memory game shuffles with sort and Math.random. Can you replace it with a Fisher-Yates shuffle so every card layout is equally likely, and explain why the old way was biased?

Field kit 02

Make it faster

Speeding up a game starts with measuring, not guessing. In Chrome, open DevTools (F12), go to the Performance tab, press record, and play for five seconds. Long blocks in the chart show where time goes. Change one thing, then measure again.

  1. Paint the background once, not every frame

    Medium

    The backdrop, wall, floor and about 20 grid lines are redrawn 60 times a second, even though they never move. On a slow laptop that's where frames get dropped.

    BuriedComplexGame.tsx:82–120 · MM3-0003, 95% sure

    In src/components/BuriedComplexGame.tsx, render3DComplex rebuilds the backdrop gradient and the floor grid every frame. Can you draw those still parts once onto an offscreen canvas and copy it each frame? Tell me how to measure the difference in Chrome DevTools.

  2. Make the canvas sharp on phones

    Medium

    The canvas is drawn at a fixed size and stretched, so it looks blurry on phones and high-resolution screens. This is about looks rather than speed, and a sharper canvas costs a little more drawing.

    BuriedComplexGame.tsx:424–427

    In src/components/BuriedComplexGame.tsx, the canvas uses WORLD_WIDTH and WORLD_HEIGHT directly. Can you size it by window.devicePixelRatio so it stays sharp on high-density screens, and scale the drawing context to match?

  3. Let the zombies glide

    MediumHidden game

    Zombies only move when the picture refreshes every 90 ms, so they hop about 11 times a second.

    ZombieSniperGame.tsx:103 · MM3-0005, 79% sure

    In src/components/ZombieSniperGame.tsx, the zombies only redraw on the 90 millisecond refresh at line 103. Can you move their positions inside the useFrame ticker so they glide every frame?

  4. Keep Snake's timer steady

    MediumHidden game

    The Snake timer is torn down and rebuilt on every single tick, because it restarts whenever the snake changes. On a slow phone the speed can wobble.

    App.tsx:181–206 · found by reading the code, checked by hand; MM3 disagreed (17%)

    In src/App.tsx, the SnakeGame interval restarts every tick because its effect depends on snake. Can you keep the snake in a ref and run one steady setInterval for the whole round?

  5. Load the fonts from index.html

    Low

    The fonts are requested from inside the stylesheet, so the browser finds them a moment later than it could.

    index.css:1 · from reading the code; MM3 passed this check

    In src/index.css, the first line loads Google Fonts with @import. Can you move it into index.html as a link tag next to the preconnect lines, and tell me if anything looks different?

  6. Copy less every heartbeat

    Low

    Each frame copies every enemy twice and walks the enemy list several times. Fine with 8 enemies. It'll matter if you ever pack rooms with far more.

    deep-signal-engine.ts:369, 445 · MM3-0002

    In src/lib/deep-signal-engine.ts, stepDeepSignalRun copies every enemy at line 369 and again at line 445. Can you copy only the enemies that actually change, and explain the before and after in plain words?

  7. Read the save once

    Low

    The header and lobby each reread and decode the whole save every time they redraw. Too small to feel today.

    App.tsx:20 and :36 · MM3-0007

    In src/App.tsx, AppShell and Lobby call getArcadeState on every render. Can you read the saved state once and pass it to the parts that need it?

  8. Before you switch the vault on: load the 3D only when needed

    Later

    Today the build leaves the 3D library out, because nothing can reach Zombie Sniper. Give it a route and the whole 3D library joins the first download, slowing the lobby for everyone. Loading it only when someone opens that game avoids that.

    App.tsx:5 · checked with a real build

    In src/App.tsx, line 5 imports ZombieSniperGame at the top. When I add a route for it, can you load it with React.lazy and Suspense so the 3D code only downloads when that game opens? Run npm run build before and after and show me the file sizes.
